# DataForge 后端修复方案与计划 - 2025-11-01

本文档根据《DataForge 后端项目审查报告》中发现的问题, 制定一套系统性的、分阶段的修复方案, 旨在将项目从当前的原型状态提升为生产就绪的、健壮可靠的企业级服务.

## 总体策略

修复工作将遵循以下分阶段的策略, 从高到低解决问题, 确保在每个阶段都能获得显着的稳定性与质量提升.

- **第一阶段: 扫清生产环境障碍 (高优先级)**: 专注于解决所有阻塞性问题, 确保项目具备部署到生产环境的基本条件.
- **第二阶段: 提升代码质量与健壮性 (中优先级)**: 专注于重构、改进错误处理和测试覆盖, 提升系统的可维护性和可靠性.
- **第三阶段: 深度优化与重构 (低优先级)**: 专注于代码的优雅性、解耦和性能优化.

---

## 详细修复计划

### 第一阶段: 扫清生产环境障碍 (预计用时: 2-3天) ✅ 已完成

#### ✅ 任务1.1: 依赖管理现代化 (已完成)

- **目标**: 解决依赖版本不固定的问题, 确保构建的可复现性.
- **具体步骤**:
    1. 安装 `pip-tools`.
    2. 创建 `requirements.in` 文件, 将 `requirements.txt` 中的直接依赖 (如 `fastapi`, `pydantic`) 移入其中, 移除开发依赖.
    3. 创建 `requirements-dev.in` 文件, 存放 `pytest`, `black` 等开发专用依赖.
    4. 运行 `pip-compile requirements.in` 和 `pip-compile requirements-dev.in` 生成版本固定的 `requirements.txt` 和 `requirements-dev.txt` 文件.
    5. 更新 `README.md`, 说明新的依赖安装方法: `pip install -r requirements.txt` 和 `pip install -r requirements-dev.txt`.
- **验证方法**: 检查新生成的 `requirements.txt` 文件是否包含所有间接依赖且版本被 `==` 固定.

#### ✅ 任务1.2: API 异步任务状态持久化 (已完成)

- **目标**: 将 API 的异步任务状态从内存迁移到 Redis, 解决数据易失性和无法水平扩展的问题.
- **具体步骤**:
    1. 在 `requirements.in` 中添加 `redis` 库.
    2. 创建一个新的配置文件 (如 `dataforge/config/settings.py`), 用于管理 Redis 连接信息等.
    3. 创建一个 Redis 连接管理模块 (如 `dataforge/core/redis_client.py`), 提供一个可复用的 Redis 客户端实例.
    4. 修改 `dataforge/api/main.py`:
        - 移除全局变量 `tasks_storage` 和 `task_counter`.
        - 在 `generate_data_async` 函数中, 使用 `uuid.uuid4()` 生成 `task_id`.
        - 将任务状态信息序列化 (如 JSON) 后存入 Redis, 使用 `task_id` 作为键.
        - 修改 `get_task_status` 和 `list_tasks` 函数, 从 Redis 中读取任务状态.
- **验证方法**: 运行异步生成任务, 重启API服务后, 依然能通过任务ID查询到正确的任务状态和结果.

#### ⏭️ 任务1.3: 数据库迁移与ORM引入 (已跳过 - 非核心功能)

- **目标**: 移除伪数据库, 为引入真实数据库和 ORM 奠定基础.
- **具体步骤**:
    1. 在 `requirements.in` 中添加 `sqlalchemy`, `psycopg2-binary` (以PostgreSQL为例) 和 `alembic`.
    2. 从代码库中完全删除 `dataforge/db/fake_db.py`.
    3. 修改 `dataforge/auth/` 目录下的相关代码, 移除对 `fake_db` 的依赖.
    4. 初始化 `Alembic` 进行数据库版本管理.
    5. 使用 SQLAlchemy 在 `dataforge/auth/models.py` 中重新定义 `User` 模型.
    6. **注意**: 这是一个大任务, 初期目标是完成模型定义和依赖引入, 完整的认证逻辑重构可在后续迭代.
- **验证方法**: 单元测试能够通过, 并且 Alembic 可以成功生成初次数据库迁移脚本.

#### ✅ 任务1.4: 安全加固 (已完成)

- **目标**: 修复CORS配置漏洞, 移除硬编码凭证.
- **具体步骤**:
    1. 修改 `dataforge/api/main.py`, 将 CORS 的 `allow_origins` 配置从环境变量读取, 并确保生产环境的默认值为一个空列表或一个安全的域名.
    2. 彻底检查并移除代码中任何残留的硬编码密码、密钥或凭证.
- **验证方法**: 在非开发模式下启动API, 检查来自不允许的域的跨域请求是否被正确拒绝.

### 第二阶段: 提升代码质量与健壮性 (预计用时: 3-4天) 🔄 进行中

#### ✅ 任务2.1: 实现统一的异常处理 (已完成)

- **目标**: 建立全局异常处理机制, 避免泄露内部错误, 提供结构化的错误响应.
- **具体步骤**:
    1. 在 `dataforge/core/exceptions.py` 中定义一套完整的业务异常.
    2. 在 `dataforge/api/main.py` 中, 使用 `@app.exception_handler(...)` 为自定义异常和通用异常 (如 `ValueError`, `Exception`) 创建处理器.
    3. 重构 `api`, `core` 等模块中的 `try...except` 块, 替换为抛出具体的业务异常.
- **验证方法**: 故意触发各种已知错误 (如找不到生成器、参数错误), 检查API是否返回统一、结构化的JSON错误响应, 并且HTTP状态码正确.

#### 🔄 任务2.2: 全面推行依赖注入 (IoC) (进行中 - 50%)

- **目标**: 解除核心组件之间的紧密耦合, 提升代码的可测试性和灵活性.
- **具体步骤**:
    1. 重构 `ConfigParser`, `GeneratorFactory` 等类, 将 `GeneratorRegistry` 等外部依赖通过构造函数注入.
    2. 移除对 `default_registry`, `default_factory` 等全局单例的直接引用.
    3. 在应用启动时 (如 `main.py` 中) 组装这些依赖.
- **验证方法**: 重构后的代码功能正常, 并且核心组件的单元测试可以在不依赖全局状态的情况下运行.

#### ⏳ 任务2.3: 完善测试套件 (待完成)

- **目标**: 补充单元测试, 增加边缘情况和异常场景的覆盖.
- **具体步骤**:
    1. 为 `factory.py`, `parser.py`, `context.py` 等核心模块编写独立的单元测试.
    2. 使用 `pytest-mock` 模拟依赖项.
    3. 为现有测试增加 `pytest.raises` 用例, 验证无效输入是否能正确触发异常.
    4. 创建 `pytest` fixture 来提供隔离的测试环境 (如独立的注册表实例), 消除测试对全局状态的依赖.
- **验证方法**: 运行 `pytest --cov`, 观察到核心模块的测试覆盖率显着提升.

### 第三阶段: 深度优化与重构 (预计用时: 2-3天) ⏳ 待开始

#### ⏳ 任务3.1: 重构生成器基类 (待完成)

- **目标**: 简化基类, 将通用策略 (如唯一性、重试) 与核心生成逻辑分离.
- **具体步骤**:
    1. 简化 `DataGenerator` 基类, 使其专注于 `generate_single` 逻辑.
    2. 创建一个或多个策略类或高阶函数 (装饰器), 用于实现唯一性保证和重试逻辑.
    3. 在 `GeneratorFactory` 或更高层中根据配置应用这些策略.
- **验证方法**: 重构后, 所有生成器的功能不变. 新的策略可以被轻松地应用或移除.

#### ⏳ 任务3.2: 配置与实现解耦 (待完成)

- **目标**: 移除 `config` 和 `api` 模块中对生成器实现细节的硬编码依赖.
- **具体步骤**:
    1. 为 `DataGenerator` 基类添加一个类方法, 如 `get_default_params()`, 用于返回其默认参数.
    2. 重构 `ConfigParser` 和 `api/main.py`, 使其动态调用此方法来获取默认值和示例, 而非从硬编码的字典中读取.
- **验证方法**: 移除硬编码字典后, 配置模板生成和API文档中的示例依然可以正常工作.
