
# 项目文档整理优化计划

**日期:** 2025年11月7日

## 1. 背景与问题分析

当前项目根目录中存在大量文档，特别是随时间生成的审查报告、修复计划和分析记录。这种结构导致了以下几个主要问题：

*   **根目录混乱：** 核心代码、项目配置与各类文档混合在一起，增加了新成员理解项目结构的难度。
*   **信息检索困难：** 文档缺乏统一的分类和组织，查找特定信息（如最终的架构方案或某个阶段的审查报告）需要浏览大量文件。
*   **命名规范不一：** 文件命名方式多样，混合了中文、英文、下划线、中划线和日期，缺乏一致性，难以通过文件名直观地了解文档内容。
*   **版本与时效性不明：** 存在多个相似主题的文档（如多个“修复方案”），难以确定哪个是最新或最终版本。

## 2. 优化目标

本次优化的核心目标是建立一个清晰、可维护、易于导航的文档体系，实现以下几点：

*   **结构清晰：** 将文档与源代码、配置文件完全分离。
*   **分类明确：** 使任何成员都能快速定位到所需类型的文档。
*   **命名规范：** 建立统一的文件命名标准，便于识别和排序。
*   **易于维护：** 为未来新增的文档提供明确的存放位置和命名指引。

## 3. 计划执行步骤

为了实现上述目标，我制定了以下分步执行计划：

### 步骤一：创建 `docs` 主目录

在项目根目录下创建一个名为 `docs` 的顶级目录。此目录将作为所有项目文档的唯一存放位置，实现文档与代码的分离。

### 步骤二：建立分类子目录结构

在 `docs` 目录下，根据文档的性质和用途，创建以下子目录结构：

*   `docs/`
    *   `guides/`: 存放核心的、相对稳定的指南性文档。
        *   `developer_guide.md` (开发者指南，可整合 `CLAUDE.md` 和 `pythoncoder.md` 的核心内容)
        *   `contributing.md` (贡献指南，从根目录移入)
        *   `registration_standards.md` (生成器注册标准，从根目录移入)
    *   `project_management/`: 存放项目规划、路线图和高级别报告。
        *   `roadmap.md` (项目路线图，可整合 `MASTER_REPAIR_ROADMAP` 等文件)
        *   `completion_reports/` (存放各阶段的最终完成报告)
    *   `audits_and_reviews/`: 存放所有具备时效性的审查、评估和分析报告。这是整理混乱文件的关键。
        *   `code_reviews/` (代码审查报告)
        *   `architecture_assessments/` (架构评估报告)
        *   `security_audits/` (安全审计报告)
        *   `test_reports/` (测试报告)
        *   `issue_analysis/` (问题分析报告，如 `pylance_type_errors`, `DUPLICATE_FILES_ANALYSIS`)
    *   `archive/`: (可选) 存放已过时但需要保留存档的旧文档。

### 步骤三：统一文件命名规范

所有迁移到 `docs` 目录下的文件都应遵循以下命名规范：

**格式：** `YYYY-MM-DD_description-of-content.md`

*   **日期 (YYYY-MM-DD):** 使用 ISO 8601 标准日期格式，便于按时间排序。
*   **描述 (description-of-content):** 使用小写英文字母和中划线 `-` 来简要描述文件内容。
*   **示例：**
    *   `项目后端审查报告_20251104.md` -> `docs/audits_and_reviews/code_reviews/2025-11-04_backend-review-report.md`
    *   `ARCHITECTURE_ASSESSMENT_2025-11-05.md` -> `docs/audits_and_reviews/architecture_assessments/2025-11-05_architecture-assessment.md`
    *   `修复方案与执行计划_20251103.md` -> `docs/project_management/2025-11-03_fix-and-execution-plan.md`

### 步骤四：文件迁移与归类（示例）

根据上述结构和命名规范，对现有文件进行迁移和重命名。以下是部分文件的迁移路径示例：

| 原文件（部分）                               | 建议目标路径                                                                              |
| -------------------------------------------- | ----------------------------------------------------------------------------------------- |
| `AGENTS.md`                                  | `docs/guides/ai-agents-guide.md`                                                          |
| `CLAUDE.md`, `pythoncoder.md`                | 整合后移入 `docs/guides/developer_guide.md`                                               |
| `CONTRIBUTING.md`                            | `docs/guides/contributing.md`                                                             |
| `README.md`, `LICENSE`                       | **保留在根目录**                                                                          |
| `ARCHITECTURE_ASSESSMENT_2025-11-05.md`      | `docs/audits_and_reviews/architecture_assessments/2025-11-05_architecture-assessment.md`    |
| `项目后端审查报告_20251104.md`               | `docs/audits_and_reviews/code_reviews/2025-11-04_backend-review-report.md`                |
| `MASTER_REPAIR_ROADMAP_2025-11-05.md`        | `docs/project_management/roadmap.md` (或作为其一部分)                                     |
| `FINAL_TEST_REPORT.md`                       | `docs/audits_and_reviews/test_reports/final-test-report.md` (建议加上日期)                |
| `pylance_type_errors_2025-11-05.md`          | `docs/audits_and_reviews/issue_analysis/2025-11-05_pylance-type-errors-analysis.md`       |

### 步骤五：更新 `README.md`

在完成文档迁移后，应更新项目根目录的 `README.md` 文件，在其中添加一个“**文档**”章节，链接到新的 `docs` 目录，并简要说明文档的组织结构，引导用户和开发者查阅。

## 4. 预期成果

完成此计划后，项目文档将达到以下状态：

*   **根目录清爽：** 只保留项目运行和协作所必需的核心文件。
*   **文档集中化：** 所有文档都位于 `docs` 目录下，易于查找和管理。
*   **结构化存储：** 通过分类目录，可以快速筛选和定位特定类型的文档。
*   **标准化管理：** 统一的命名规范使得文档管理更加高效和直观。
