### **DataForge 项目全面详细规则**

#### **1. 编码规范 (Coding Standards)**

遵循“代码整洁之道”和Python最佳实践，确保代码可读、可维护、可测试。

1. **PEP 8 规范**:

    - **强制执行**: 所有Python代码必须严格遵循 [PEP 8](https://peps.python.org/pep-0008/ "null") 编码风格指南。

    - **工具**: 使用 `Black` 进行代码格式化，`isort` 进行导入排序，`ruff` 进行静态代码分析，并在CI/CD流程中强制检查。

2. **命名约定**:

    - **变量/函数**: 使用 `snake_case` (例如: `user_name`, `generate_data`)。

    - **类**: 使用 `CamelCase` (例如: `DataGenerator`, `IDCardGenerator`)。

    - **常量**: 使用 `ALL_CAPS` (例如: `DEFAULT_BATCH_SIZE`)。

    - **私有成员**: 使用单下划线前缀 (`_private_method`) 表示内部使用，双下划线前缀 (`__private_attribute`) 避免子类名称冲突。

3. **类型提示 (Type Hints)**:

    - **强制使用**: 所有函数参数、返回值和关键变量必须使用类型提示。

    - **工具**: 使用 `mypy` 进行静态类型检查，并在CI/CD流程中强制检查。

4. **注释与文档字符串 (Docstrings)**:

    - **函数/方法**: 所有公共函数和方法必须包含符合 [PEP 257](https://peps.python.org/pep-0008/ "null") 规范的文档字符串，清晰描述其目的、参数、返回值、可能抛出的异常。

    - **复杂逻辑**: 复杂代码块必须有行内注释解释其意图。

    - **模块/类**: 模块和类必须有顶层文档字符串，概述其功能。

5. **代码复用与抽象**:

    - **DRY 原则**: 避免重复代码 (Don't Repeat Yourself)。提取通用逻辑为函数或类。

    - **高内聚低耦合**: 模块内部功能紧密相关，模块间依赖最小化。

    - **接口优先**: 优先定义清晰的接口（抽象基类），再实现具体逻辑。

6. **错误处理**:

    - **显式异常**: 使用自定义异常类来表示特定业务错误，而不是返回 `None` 或布尔值来表示失败。

    - **捕获与处理**: 仅捕获已知如何处理的异常。对于无法处理的异常，必须允许其冒泡或进行适当的日志记录。

    - **日志记录**: 详细记录错误信息，包括堆栈跟踪，但必须避免记录敏感数据。


#### **2. 架构与设计原则 (Architecture & Design Principles)**

确保系统具备良好的可扩展性、性能、安全性和可维护性。

1. **模块化设计**:

    - **职责单一**: 每个模块或类只负责一项明确的功能。

    - **清晰边界**: 模块之间通过明确定义的接口进行交互，减少直接耦合。

    - **目录结构**: 采用逻辑清晰的目录结构，例如：

        ```
        dataforge/
        ├── cli/
        ├── api/
        ├── core/
        │   ├── orchestrator.py
        │   ├── config_manager.py
        │   ├── generator_factory.py
        │   ├── validation_module.py
        │   └── output_module.py
        ├── generators/
        │   ├── __init__.py
        │   ├── basic_info/
        │   │   ├── name_generator.py
        │   │   └── id_card_generator.py
        │   ├── identifiers/
        │   └── ...
        ├── data/ (静态参考数据)
        ├── tests/
        ├── docs/
        ├── config/
        └── main.py
        ```

2. **可扩展性**:

    - **插件机制**: 严格遵循 `DataGenerator` 抽象接口和 `setuptools` entry points 机制，确保新的数据生成器可以无缝集成。

    - **配置驱动**: 必须通过配置而非代码修改来改变系统行为。

3. **性能优化**:

    - **I/O 优化**: 充分利用异步I/O (例如在FastAPI和输出模块中) 来处理并发请求和文件操作。

    - **内存管理**: 对于大规模数据生成，采用流式处理和生成器模式，避免一次性加载所有数据到内存。

    - **参考数据缓存**: 将不经常变化的参考数据加载到内存中以提高查询速度。

4. **安全性**:

    - **输入验证**: 对所有用户输入（CLI参数、API请求体、配置文件）进行严格的格式和逻辑验证。

    - **敏感数据处理**: 避免在日志、配置或非加密存储中记录敏感信息。

    - **依赖安全**: 定期审计第三方库的漏洞。

    - **注入防护**: 在生成SQL `INSERT` 语句时，必须使用参数化查询或适当的转义，防止SQL注入（尽管是生成，也要确保生成的SQL是安全的）。


#### **3. 测试策略与质量保证 (Testing Strategy & Quality Assurance)**

确保 `DataForge` 自身生成的数据是高质量的，并且工具本身是可靠的。

1. **测试覆盖率**:

    - **目标**: 核心业务逻辑（数据生成算法、校验逻辑）的单元测试覆盖率必须不低于80%。

    - **工具**: 使用 `pytest` 作为测试框架，`pytest-cov` 统计覆盖率。

2. **单元测试**:

    - **粒度**: 针对每个 `DataGenerator` 子类、配置解析器、输出格式化器等独立组件编写单元测试。

    - **断言**: 明确断言预期行为和异常情况。

    - **Mocking**: 使用 `pytest-mock` 隔离外部依赖（如文件系统、数据库）。

3. **集成测试**:

    - **CLI 集成**: 测试CLI命令能否正确解析参数、调用核心逻辑并产生预期输出。

    - **API 集成**: 测试FastAPI端点能否正确处理请求、调用后端服务并返回响应。

    - **端到端测试**: 模拟真实用户场景，验证从输入到输出的完整流程。

4. **数据真实性与准确性验证**:

    - **关键数据类型**: 对身份证号、银行卡号、统一社会信用代码等具有明确校验规则的数据类型，必须编写大量测试用例，确保生成的每个数据都符合其校验逻辑。

    - **关联性验证**: 必须编写测试用例验证关联字段（如身份证号与年龄、性别）之间的一致性。

    - **边界值/异常值测试**: 必须专门针对边界值、极端值、非法格式的数据生成进行测试，验证系统对这些情况的处理能力。

5. **性能测试**:

    - **基准测试**: 针对不同数据类型和生成数量，建立性能基准。

    - **负载测试**: 使用 `Locust` 对API服务进行负载测试，评估在并发请求下的吞吐量和延迟。

    - **内存占用**: 监控大规模数据生成时的内存消耗。


#### **4. 文档规范 (Documentation Standards)**

清晰、全面的文档是项目成功的关键。

1. **项目文档 (README.md)**:

    - **内容**: 包含项目简介、安装指南、快速开始、CLI使用示例、API接口说明、贡献指南。

    - **更新**: 必须保持与代码同步更新。

2. **代码文档 (Docstrings)**:

    - 如编码规范所述，所有公共API（函数、类、方法）必须有详细的文档字符串。

    - 使用Sphinx工具从代码中自动生成API文档。

3. **设计文档**:

    - **架构设计**: 维护高层次的架构图和组件说明。

    - **数据类型设计**: 详细描述每种数据类型的生成逻辑、参数、校验规则、关联性。

    - **决策记录**: 记录关键技术选型和设计决策的权衡分析 (Architecture Decision Records - ADRs)。

4. **用户指南**:

    - 提供详细的用户指南，解释如何使用 `DataForge` 生成各种类型的数据，包括高级定制和特殊场景。

    - 包含常见问题 (FAQ) 和故障排除指南。


#### **5. 版本控制与协作 (Version Control & Collaboration)**

采用标准化的Git工作流，确保团队高效协作。

1. **Git Flow**:

    - **主分支**: `main` 分支始终保持可部署状态。

    - **开发分支**: `develop` 用于日常开发集成。

    - **特性分支**: 每个新功能或Bug修复都在独立的特性分支上开发 (例如: `feature/add-id-card-generator`, `bugfix/fix-phone-validation`)。

    - **Pull Request (PR)**: 所有代码修改必须通过PR提交，并经过至少一名团队成员的代码审查。

2. **提交信息 (Commit Messages)**:

    - **规范化**: 遵循 [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/ "null") 规范，例如 `feat: add new data type` 或 `fix: resolve validation bug`。

    - **清晰简洁**: 提交信息必须清晰、简洁地描述本次提交的目的和内容。

3. **代码审查 (Code Review)**:

    - **强制执行**: 所有PR必须经过至少一名经验丰富的团队成员审查通过后才能合并。

    - **关注点**: 可读性、可维护性、性能、安全性、测试覆盖率、设计模式、错误处理。


#### **6. 部署与运维规范 (Deployment & Operations Guidelines)**

确保 `DataForge` 能够稳定、高效地运行。

1. **容器化**:

    - **Docker**: 所有部署必须基于Docker镜像。

    - **镜像优化**: 遵循Docker最佳实践，构建小巧、安全的镜像（例如，多阶段构建）。

2. **CI/CD**:

    - **自动化流水线**: 必须建立完整的CI/CD流水线，实现代码提交 -> 自动化测试 -> 镜像构建 -> 镜像推送 -> 自动化部署。

    - **环境隔离**: 必须区分开发、测试、生产环境，并确保不同环境的配置隔离。

3. **监控与告警**:

    - **指标**: 监控API服务的请求量、响应时间、错误率、资源使用（CPU、内存）。

    - **日志**: 集中化日志管理，方便问题排查。

    - **告警**: 配置关键指标的告警，及时发现并响应异常情况。

4. **可观测性**:

    - **结构化日志**: 使用结构化日志 (如JSON格式)，便于日志分析工具处理。

    - **链路追踪**: 如果 `DataForge` 成为微服务架构的一部分，必须引入分布式链路追踪。


#### **7. 安全规范 (Security Guidelines)**

将安全内嵌到开发生命周期的每个阶段。

1. **最小权限原则**:

    - 服务运行账户、数据库连接等必须只拥有完成其任务所需的最小权限。

2. **敏感数据保护**:

    - **配置管理**: 敏感配置（如API密钥、数据库凭证）不得硬编码，必须通过环境变量或Secrets Manager注入。

    - **日志**: 严禁在日志中输出敏感用户数据或凭证。

    - **传输加密**: API通信必须使用HTTPS。

3. **输入验证与过滤**:

    - 对所有来自外部的输入进行严格的验证、净化和编码，防止常见的Web漏洞（SQL注入、XSS、命令注入、路径穿越）。

    - 即使是生成测试数据，也必须确保生成的“恶意”payload是可控的，并且在实际应用中不会意外执行。

4. **依赖安全**:

    - 定期使用 `Snyk` 和 `Dependabot` 等安全扫描工具检查项目依赖中的已知漏洞。

    - 及时更新有安全漏洞的依赖。


#### **8. 项目管理与沟通 (Project Management & Communication)**

采用敏捷开发方法，促进团队内部和与外部的有效沟通。

1. **敏捷开发**:

    - **Scrum**: 采用Scrum框架进行迭代开发。

    - **短周期迭代**: 设定短期的迭代周期（例如1-2周），快速交付可工作的功能。

    - **每日站会**: 每日进行简短站会，同步进度、问题和计划。

2. **任务管理**:

    - 使用Jira等项目管理工具跟踪任务、Bug和用户故事。

    - 任务拆分必须遵循我们之前讨论的最小粒度原则。

3. **沟通**:

    - **透明化**: 所有关键决策和进度必须透明化，及时同步给团队成员和相关方。

    - **问题解决**: 鼓励开放讨论，通过技术评审、设计评审等方式共同解决复杂问题。

    - **反馈**: 积极收集用户和测试团队的反馈，并将其纳入产品改进。


这些规则将作为 `DataForge` 项目开发和维护的基石。它们是明确且强制执行的，确保团队对这些规则的理解、认同和持续遵守。
