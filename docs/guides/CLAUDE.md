## Project Overview

DataForge is a high-efficiency, flexible, and highly configurable test data generation tool focused on providing high-quality, realistic, and diverse test data for software testing teams, with deep optimization for Chinese localization data generation.

**Core capabilities**: Chinese ID cards, bank cards, phone numbers, unified social credit codes, addresses, names, and other localized data types with field relationship support.

## Architecture

### Core Design Principles
- **Plugin-based Architecture**: Generators are registered via setuptools entry points and factory pattern
- **Type Safety**: Full type hints with mypy static checking enforced
- **Performance**: Stream processing, async I/O, data preloading for large-scale generation
- **Extensibility**: Abstract `DataGenerator` base class with clear interface contracts

### Key Components

**Core Modules** (`dataforge/core/`):
- `generator.py`: Base `DataGenerator[T]` abstract class - all generators inherit from this
- `factory.py`: `GeneratorRegistry` and `default_factory` for generator registration/creation
- `relations.py`: `DataRelationManager` handles inter-field data relationships
- `validator.py`: Validation logic for generated data
- `cache.py`: Caching mechanism for performance optimization
- `preloader.py`: Background data preloading for frequently used static data
- `exceptions.py`: Custom exception hierarchy (`DataGenerationError`, `GeneratorConfigError`, etc.)

**Generator Categories** (`dataforge/generators/`):
```
generators/
├── basic/          # Name, age, gender, marital status
├── contact/        # Phone, email, landline, verification codes
├── identifier/     # ID card, bank card, USCC, passport, driver's license
├── finance/        # Financial data generation
├── network/        # IP, MAC, URL, device ID, session tokens
├── numeric/        # Numbers, ranges, distributions
├── text/           # Strings, Chinese text, multilingual, special chars
├── auth/           # Passwords, usernames, tokens
└── advanced/       # Complex composite generators
```

**Configuration** (`dataforge/config/`):
- `parser.py`: `ConfigParser` handles YAML/JSON config files and CLI arguments
- `settings.py`: Global configuration and defaults

**Output** (`dataforge/output/`):
- `formatter.py`: `OutputFormatter` coordinates output format handling
- `json.py`, `csv.py`, `xml.py`, `sql.py`: Format-specific output modules

**Interfaces** (`dataforge/cli/`, `dataforge/api/`):
- `cli/main.py`: Click-based CLI using argparse
- `api/main.py`: FastAPI async web service

### Generator Interface Contract

All generators MUST implement:
```python
class CustomGenerator(DataGenerator[T]):
    def _setup(self) -> None:
        """Initialize generator-specific state from self.parameters"""
        pass

    def generate_single(self, context: Optional[GenerationContext] = None) -> T:
        """Generate single data item (required)"""
        pass

    def validate(self, data: T) -> bool:
        """Validate generated data (required)"""
        pass

    @property
    def generator_type(self) -> GeneratorType:
        """Return generator category (required)"""
        pass

    @property
    def supported_parameters(self) -> list[str]:
        """Return list of supported parameter names (required)"""
        pass

    # Optional overrides:
    def generate_batch(self, count: int, context: Optional[GenerationContext] = None) -> list[T]:
        """Override for batch optimization"""
        pass
```

### Data Relationship System

The `DataRelationManager` (in `core/relations.py`) handles field dependencies:
```python
# Example: Age derived from ID card birthdate
relation_manager.add_relation(
    source_field="idcard",
    target_field="age",
    relation_type="derived",
    extractor=lambda idcard: calculate_age_from_idcard(idcard)
)
```

When generating related data, use `GenerationContext.related_data` to pass dependent values.

### Registration Mechanism

Generators are auto-registered via:
1. **Decorator**: `@register_generator('name', ['alias1', 'alias2'])`
2. **Entry points**: Defined in `pyproject.toml` under `[project.entry-points."dataforge.generators"]`
3. **Auto-import**: `dataforge/__init__.py` imports all generator modules to trigger registration

## Code Style Requirements

### Mandatory Standards (enforced in CI/CD)
- **PEP 8**: Strictly enforced via Black formatter (line length: 88)
- **Type hints**: All function signatures, returns, and key variables MUST be typed
- **Docstrings**: PEP 257 format for all public functions/methods/classes
- **Import sorting**: isort with Black profile
- **Linting**: ruff with configuration in `pyproject.toml`

### Naming Conventions
- Variables/functions: `snake_case` (e.g., `user_name`, `generate_data`)
- Classes: `CamelCase` (e.g., `DataGenerator`, `IDCardGenerator`)
- Constants: `ALL_CAPS` (e.g., `DEFAULT_BATCH_SIZE`)
- Private members: `_single_underscore` prefix for internal use
- Name mangling: `__double_underscore` prefix only when needed for subclass isolation

### Error Handling
- Use custom exceptions from `core/exceptions.py` hierarchy
- Never return `None` or booleans to indicate errors - raise explicit exceptions
- Log errors with stack traces but avoid logging sensitive data
- Only catch exceptions you can meaningfully handle

## Performance Considerations

### Optimization Techniques Used
- **Async I/O**: FastAPI endpoints and file output use async/await
- **Batch processing**: Override `generate_batch()` for optimized bulk generation
- **Caching**: `core/cache.py` provides LRU caching for expensive operations
- **Preloading**: `core/preloader.py` loads static data on startup in background
- **Stream processing**: Use generators/iterators for large datasets to avoid memory overhead
- **Memory management**: Avoid loading all data at once; process in chunks

### When Optimizing
- Profile first with pytest-benchmark or cProfile
- Focus on batch generation paths (most common use case)
- Cache validation logic results where possible
- Preload static reference data accessed frequently

## Security Requirements

- **Input validation**: All user inputs (CLI args, API requests, config files) validated via Pydantic models
- **No secrets in code**: Never hardcode credentials, API keys, or sensitive data
- **Logging safety**: Never log generated ID cards, bank cards, or other sensitive test data in production
- **Dependency security**: Run safety checks on dependencies regularly
- **SQL injection prevention**: Use parameterized queries in SQL output module

## Special Notes

### Chinese Localization
- ID card generation follows GB 11643-1999 standard with region codes
- Bank card uses Luhn algorithm for checksum validation
- Phone numbers use actual operator prefixes for realism
- USCC (统一社会信用代码) follows GB 32100-2015 standard
- Addresses based on real administrative divisions

### Relationship Handling
When implementing generators with relationships:
1. Check `context.related_data` for dependent field values
2. Register relationships in `default_relation_manager` if not already present
3. Document relationship requirements in generator docstring

### Plugin Development
To create custom generators:
1. Inherit from `DataGenerator[T]` with appropriate type
2. Implement all abstract methods and properties
3. Register via `@register_generator` decorator
4. Add entry point in `pyproject.toml` if distributing separately
5. Add unit tests in `tests/generators/`
